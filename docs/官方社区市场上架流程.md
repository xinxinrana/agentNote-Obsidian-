# agentNote 官方社区市场发布流程

> English copy: [Obsidian Community Listing Guide](Obsidian%20Community%20Listing%20Guide.md)

本流程用于发布新版本和处理官方审核，不绑定某个历史版本。仓库为 [xinxinrana/agentNote-Obsidian-](https://github.com/xinxinrana/agentNote-Obsidian-)。已上架插件的后续版本沿用原条目，不新建条目。

## 分工

| 事项 | 我主导 | 你辅助 |
| --- | --- | --- |
| 代码、文档、测试与构建 | 整理范围、验证产物 | 确认功能与文案 |
| 本地 Obsidian 验收 | 部署到测试 vault，给出核对项 | 在 Obsidian 中确认真实交互 |
| GitHub 提交与 Release | 在获得授权后执行，核对附件 | 确认发布范围，完成必要的账号授权 |
| 社区目录审核 | 分析审核结果、修复问题 | 完成账号绑定、条款确认及需要本人操作的提交 |

## 1. 确定版本与范围

确认要公开的功能和版本号。`manifest.json`、`package.json`、`package-lock.json` 与 GitHub Release Tag 保持一致，使用尚未发布过的 `X.Y.Z`，不要复用旧 Tag。

`manifest.json` 应与实际功能一致：插件 ID 为 `agentnote`；使用本地文件系统和 HTTP 服务，因此为桌面端插件；最低 Obsidian 版本须覆盖实际调用的 API。`README.md` 保持英文默认入口，提供中文说明链接。

**我负责**核对版本、功能范围和公开材料；**你负责**确认最终功能与文案。

## 2. 检查公开仓库

- 根目录包含 `LICENSE`、`README.md`、`manifest.json`、`styles.css` 和可构建的源码。
- README 说明安装、使用、隐私和限制；截图与相对链接可正常打开。
- 不提交测试 vault、个人笔记、运行数据、凭据、私人路径或会话文件。
- 发布前查看 `git status` 和完整 diff，只纳入本次确认的文件。

**我负责**检查仓库和构建材料；**你负责**确认是否存在不应公开的内容。

## 3. 本地质量验证

在仓库根目录运行：

```powershell
npm run typecheck
npm run build
node test/e2e.mjs
npm run test:git-sync
git diff --check
```

将 `main.js`、`manifest.json`、`styles.css` 部署到**测试 vault**，在 Obsidian 里检查：

- 插件正常启用、接入台和知识档案可打开。
- Claude Code、Codex、WorkBuddy 始终展示；未安装时官网入口可用。
- 已安装 agent 的接入、默认说明更新、自定义提示词和移除功能可用。
- 本地服务响应 `/api/health`；文件、文件夹和选段分享能读取，笔记可新建和更新。
- 知识档案中的资料标题能打开原文件；隐私展示时不暴露标题和打开入口。
- 反馈表单能复制报告，并按用户选择在系统默认浏览器打开预填的 GitHub Issue 或反馈站。

**我负责**自动检查和测试部署；**你负责**确认 Obsidian 中的界面与交互。测试 vault 的插件文件可以覆盖，真实 vault 的笔记及 `agentNote/data/*.json` 不在部署范围内。

## 4. 提交与发布 GitHub Release

确认改动后提交并推送默认分支。基于已推送的提交创建同版本 Release，将以下三个文件作为**Release 附件**直接上传：

- `main.js`
- `manifest.json`
- `styles.css`

示例命令中的版本号要替换为本次实际版本：

```powershell
gh release create X.Y.Z main.js manifest.json styles.css --target main --title "X.Y.Z" --generate-notes
```

发布后检查 Tag、Release 附件和构建验证结果。仓库中仅有源文件或构建输出，不能代替 Release 附件。**我负责**在授权可用时执行和核验；**你负责**批准发布范围，并在需要时完成 GitHub 登录或二次验证。

## 5. 社区目录与审核

已有 agentNote 条目时，在原条目查看新版本审核结果；如目录未及时识别 Release，可在管理页使用检查新版本和请求复查的入口。不要为每个版本重复创建插件条目。

首次提交时，**你负责**登录 Obsidian 社区账号、连接 GitHub、选择 Owner、同意开发者政策并完成最终提交；这些个人账号和法律确认不能由我代替。**我负责**核对条目内容、版本、报错及修复方案。

审核报告须区分错误、警告和建议。错误按具体信息修复并用递增版本重新发布；警告先评估功能影响，不为清除警告牺牲兼容性或用户数据。审核页面的“预览完成”不等于正式 Release 审核通过，应核对最新版本对应的结果。

## 6. 上线后验收

从社区插件目录安装或更新 agentNote，而不是只验证本地测试副本。确认显示版本与 Release 一致，插件能启用，分享地址可读取，agent 能写入，设置页可检查更新。若社区目录暂未更新，先核对最新 Release 和该版本的审核状态。

## 不能独立完成的事项

- 你的 GitHub 或 Obsidian 账号登录、二次验证和授权。
- 首次上架时的 Owner 选择、开发者条款确认和最终提交。
- 未授权情况下的仓库推送或 Release 发布。
- 你在真实 Obsidian 环境中的最终验收。
